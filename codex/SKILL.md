# Orchestrate in Codex

The physical parent of this skill directory is the kit root. Resolve it with `realpath` before using paths below. The kit contains `contracts/`, `failure-checklist.md`, `agents/`, and `scripts/orch`. Work in the user's target repository, not in the kit.

Codex does not load the Claude agent frontmatter or enforce its guard hook. When dispatching a role, tell the agent to read the body of its `agents/<role>.md` file and the matching contract, replacing `~/.claude/skills/orchestrate/` with the kit root. Ignore Claude-only model names, tool, hook, and permission instructions; use the Codex routing below. The designer uses impeccable when available and otherwise derives the spec from the project's UI. Enforce each role's write boundaries in the dispatch and check `git status` after it finishes. Follow the current session's permissions and agent availability; never claim the Claude guard protects a Codex run.

When the user explicitly requests Herdr pane agents, read [herdr.md](herdr.md) before dispatching roles. Otherwise use Codex collaboration agents when available; they have no Herdr pane IDs.

## Model routing

Set the model and reasoning effort explicitly for each role, using the plan's task tag:

| Role | Model | Effort |
| --- | --- | --- |
| Architect and Designer | `gpt-6.1-sol` | `high` |
| Engineer, `[mechanical]` | `gpt-6-luna` | `low` |
| Engineer, `[judgment]`; any repair | `gpt-6.1-sol` | `medium` |
| Task QA and final QA | `gpt-6.1-sol` | `medium` |

Use `high` effort for final QA when the diff exceeds about 1,500 changed lines or crosses auth or concurrency boundaries. For collaboration agents, pass both `model` and `reasoning_effort` with `fork_turns="none"` and include all role and input paths because they do not inherit the parent conversation. For Herdr agents, pass both at startup as described in [herdr.md](herdr.md). If a routed setting is unavailable, report that before dispatching; never silently inherit or substitute it.

## Run

1. Check the target repo's rules, branch, and `git status --porcelain`. If the tree has user changes, preserve them and ask how to proceed before branch or commit operations. Make a slug from the request and run `scripts/orch workspace <slug>`. Resume from `.orchestrate/<slug>/ledger.md` and git history if present. Start the ledger with its usual heading; record later stage and task events through `scripts/orch log <slug> '<event>'`. It timestamps the ledger and refreshes the **target repo's** `.dagr/run.json` from those events when the validator is installed. Share that absolute path with the user; a pane watching the skill kit's `.dagr/run.json` will not see another repo's run. Use `scripts/orch dagr <slug>` to rebuild it. Do not infer a task's completion from an agent going idle.
2. Plan in `tasks/todo.md` using `contracts/plan.md` and `failure-checklist.md`. For a change of at most two files with no schema, API, auth, concurrency, or cross-screen impact, write one task directly. Otherwise, dispatch an architect if collaboration or requested Herdr pane agents are available and delegation is permitted. If the plan touches UI, dispatch a designer to write `.orchestrate/<slug>/design-spec.md`, then fold its checkable items into the plan. Use the corresponding `agents/` instructions for these roles. Keep planning agents' writes to the plan and `.orchestrate/` only.
3. Show the plan, task digest, open questions, and design spec if any. Run `scripts/orch flow <slug>` for the flow; provide its file path if opening a local browser is unavailable. Log `STAGE: Approve`, ask the user to **Approve / Revise / Stop**, and log `Plan approved` only after their yes. Revise the plan and show it again until approved. Do not build before approval. `--eval` may auto-approve only when the user explicitly requests that mode; log `Plan auto-approved (eval)` in that case.
4. After approval, create the planned branch and commit the plan. Before each task, list agents and stop any finished agent still waiting on background work; only the current engineer may edit the shared checkout. Record the pre-task commit and run `scripts/orch brief <slug> N`. Dispatch one engineer with the model and effort from its task tag to implement, check, and commit that task. Log `Task N: start base=<sha> model=<m> effort=<e> agent=<actual id>` after dispatch, adding `pane=<Herdr pane id>` only for a pane-hosted agent. Set `m` and `e` to the settings actually used. Use `agents/engineer.md` and `contracts/engineer-report.md`; include the brief and design spec paths. Keep tasks sequential. Never send the engineer's report to QA. Require a report with DONE or DONE_WITH_CONCERNS before QA; log `Task N: review`. For NEEDS_CONTEXT, BLOCKED, a missing report or an unknown status, log `Task N: needs you reason=<why>` and resolve it before QA.
5. Run `scripts/orch package <slug> <pre-task commit> HEAD`, then dispatch a fresh QA agent with the brief, package, checklist, and `contracts/qa-report.md`. QA reads and tests but writes only under `.orchestrate/`. Check the worktree after QA. Run `scripts/orch qa-head <qa report>` to verify its verdict and Range against current HEAD, then log `Task N: QA r<k> <PASS|FAIL|BLOCKED> head=<returned sha> report=<path>`. On PASS, log `Task N: complete head=<same sha> qa=PASS`. On FAIL, log `Task N: fix round <k> model=<m> effort=<e> agent=<actual id>` after dispatching the repair, using `gpt-6.1-sol` at `medium` effort even if the original task was `[mechanical]`, and adding `pane=<Herdr pane id>` only for a pane-hosted agent. A failed Luna engineer needs a fresh Sol agent; a Sol engineer can handle its own repair. Allow up to two fix rounds, then escalate unresolved findings. On BLOCKED, log `Task N: needs you reason=qa-blocked`, report the exact missing check or permission, and wait for direction. Run one final QA pass on the full branch for multi-task changes; require its PASS report, run `qa-head`, and save its reviewed HEAD. If product code changes afterwards, repeat final QA.
6. Add actionable lesson candidates to `tasks/lessons.md`, complete the plan's Review section, and commit those documentation changes. Before handoff, run `scripts/orch handoff-head <final reviewed sha>` (the sole task QA for a one-task run, whole-branch QA otherwise). It permits only committed changes to those two files after QA; any product change requires another QA pass. Stop any run agent still active after its verified report. Keep the target repo's final `.dagr/run.json` so the completed run remains visible; restore or remove only temporary mirrors made in other workspaces. Report both SHAs if they differ, plus the branch, commits, task verdicts, commands run, changed files, and human follow-ups. Record usage with `scripts/orch usage` only when agent token counts are actually available. Do not invent counts.

If neither collaboration nor requested Herdr pane agents are available, or delegation is disallowed, perform the stages in the main session, keep separate plan and QA passes, and state clearly that QA was not independent. Never push, merge, deploy, modify production, drop data, or rewrite history as part of the pipeline. Request separate authorization for any later handoff action.

When testing this skill itself, run the focused helper checks first. A full multi-agent fixture consumes separate agent usage; run one only when the user asks for an end-to-end pipeline test. Keep the same QA requirements for actual software changes.
